# Provider Capability Matrix (V1) — GitHub vs GitLab

This matrix prevents "guessing" provider behaviors during implementation.

## Anchors (official docs)

- GitHub "Create or update file contents": requires `repo` (classic PAT) and **also `workflow`** when modifying `.github/workflows/*`.
- GitLab "Create a project": `POST /projects` via Projects API.
- Backstage scaffolder supports GitHub/GitLab action modules (validates that parity is achievable).

---

## Capability table

| Action | GitHub implementation | GitHub permissions | GitLab implementation | GitLab permissions |
|--------|-----------------------|---------------------|------------------------|---------------------|
| `scm.createRepo@v1` | Create repo endpoint (REST) | repo create in org/user (App/fine-grained recommended) | `POST /projects` | token with project create rights (api scope typical) |
| `scm.createOrUpdateFile@v1` | `PUT /repos/{owner}/{repo}/contents/{path}` | classic PAT: `repo`, plus `workflow` if path under `.github/workflows/*` | repository file create/update API (provider adapter) | maintain/write rights to repo (token scope depends on GitLab auth mode) |
| `scm.pushSkeleton@v1` | repeated `createOrUpdateFile` | same as above | repeated file ops | same as above |
| `scm.openPrOrMr@v1` | Pull Request API | repo write | Merge Request API | developer+ rights |
| `scm.ensureWebhook@v1` | Webhooks API | repo admin / hook manage | Project hooks API | maintainer+ |
| `catalog.registerEntity@v1` | internal DB write | n/a | internal DB write | n/a |
| `docs.bootstrap@v1` | file writes (`docs/*`) | `repo` | file writes | write rights |
| `ci.bootstrap@v1` | write `.github/workflows/ci.yml` | `repo` + `workflow` for classic PAT | write `.gitlab-ci.yml` | write rights |
| `k8s.bootstrap@v1` | file writes | `repo` | file writes | write rights |
| `scorecards.evaluate@v1` | internal checks + optional SCM reads | repo read | internal checks + optional SCM reads | repo read |

## Implementation notes (do this in code)

1) **Capability detection**  
Expose `GET /api/integrations/scm/capabilities` so UI/templates can disable unsupported paths per installation.

2) **Least privilege on GitHub**  
Prefer GitHub App / fine-grained tokens and only grant "Workflows: write" when you actually need to touch `.github/workflows/*`.

3) **Docs pipeline (V2)**  
If you later implement TechDocs-style static builds, Backstage TechDocs reader fetches static files generated by MkDocs and served by techdocs-backend.
